## 1. 一句话概念

**一册沿着两个人的人生轨迹翻阅的相册。** 2016 年短暂相识，此后各自生活，真实的朋友圈互动像疏密不同的星群一样留下联系；2025 年重新连接，2026 年的时间突然变得丰盛。它装得下精心留下的照片，也留得住那些幸福到来时，根本顾不上拍下的瞬间。

最核心的视觉形式是 **双轨时间轴**；最核心的时间体验是 **从十年远景进入 2026 年的局部放大**；最核心的情绪表达是 **照片与留白并存**。不是恋爱史考试、不是第二本情书，也不是必须看完才能参与生日仪式的任务。

## 2. 设计原则

1. **关系不等于物理距离。** 两条轨迹代表各自生活与共同在场，不是感情强弱。2016 年初识短暂相交；2016–2025 年大多分开；2025 年重新连接；2026 年异地时分开但保持联系，真正线下相聚的时段自然汇合。未来仍允许分开再汇合。
2. **时间线既是内容又是导航。** 玩家翻页，时间指针顺势移动；点击有内容的节点，相册跳到对应记忆。没有素材的年份仍在轴上存在，不编造内容。
3. **长期少聊天，但朋友圈联系并不稀少。** 已取得 952 条双向互动的日期与方向记录，其中 2016-02-14 至 2025-11-12（重新联系前）有 **778 条**。两人发朋友圈的频率不同，因此画册不比较点赞方向与双方数量，只将互动总量按时间聚合成星群，保留不同年份的疏密起伏；指针经过时星群依次短暂亮起、再熄灭，不可点击，也不列出具体点赞内容。另有两颗独立的**早年聊天亮星**：2017-07-27「在不」、2019-01-13「谢谢大兄弟」，与点赞星群使用不同图形。悬停提示原句，不作为跳转节点。
4. **相遇前的记录不需要对称。** 有时只出现一人的照片；有时同一时期双人对照。不是每一年都强制凑两个人，也不要求照片意义相似。
5. **记录形式随生活改变。** 相识之前排版更克制、独立；2026 年图片、票根、小标签、私人语言与琐碎物件逐渐多起来。但相册仍保持统一的纸张与字体系统。
6. **留白不是遗憾教育。** 两人都爱拍照、想记录生活。跨年忘了截图、求婚没有拍摄，是幸福来时正在亲自经历。空相框不补造真实截图，也不说“不要执着出片”。
7. **让照片说话。** 每个单元以图片／物件／日期为主，少量真实文字作注解；完整情书仍归 E04。不要把原始聊天统计、研究笔记和所有情话全部塞入页面。
8. **她走出第一步，剩下的路他来奔赴。** 求婚词首句「谢谢走出的第一步／剩下的路我都会勇敢向你奔赴」作为全册首尾呼应。前半段她的轨迹上标出几次“先开口”（2017「在不」、2025-11-13「又是一个时差党」、2026-01-01「是的吧？」）；从 2026 起，脚印换到他的轨迹：02-23 飞回宜昌、09-19 回国、10-03 求婚、10-19 领证，并向未来继续延伸。两组脚印必须成对出现，避免读成“一直是她在主动”。

## 3. 交互与版式

### 3.1 载体

在客厅电视下方的柜面放置一册可辨认的实体相册（2026-10-28 用户确认）。玩家靠近按 `F` 阅读；镜头保留客厅的空间感，但翻阅时优先保障照片、文字与底部时间轴清楚可见。退出 `Esc` 返回原位置，本次游玩记住最近阅读单元。不进入背包，不影响王冠、蛋糕、2048 或仪式条件。

首版使用**双页手账／相片册**：米白纸张、轻微纸张纹理、照片角贴／胶带／票根／随手批注；不必模拟复杂物理翻书。2026 前的单人页、双人对照页和 2026 后的拼贴页共用同一外壳，但内部自由排版。

### 3.2 底部横向双轨时间带（已确认）

时间带**横跨整本展开画册的下沿**，作为页面中的固定区域，而不是悬浮在顶部的网页式导航，也不是挤在侧面的章节书签。建议先分配画册可用高度的 **15–20%**，余下留给照片和文字，实际按 1366×768 的阅读效果微调。

- 两条柔和、略有手绘感的曲线分别代表放仔与莹仔；色彩区别但不强制每页写归属标签。
- **记忆节点**（可点击）连接到对应画册单元；**季度星群**（不可点击）代表实际找到的互动记录的时间聚合；**当前时间指针**随页面改变。
- 单人记忆仅高亮相应轨迹，双人对照同时高亮两条轨迹；共同生活中真正同处时，两条轨迹在视觉上短暂合为一条。
- 玩家从 2017 翻到 2020 等跨度较大的节点时，指针走过中间的空白年份。经过的季度星群按时间顺序亮起、熄灭；不逐条打开，不因某个季度几十次互动而重复几十段动画，也不强制播放很长的过场。
- **脚印**：她的“第一步”以小脚印标在她的轨迹上；2026 年他奔赴的几步标在他的轨迹上。脚印是装饰性说明，不是额外可点击节点。
- **通话针脚**：2026 年异地的时段，两条线之间画一排细针脚，疏密对应当月视频通话时长（1 月 99.8h 最密，4–7 月每月 80h+，9 月后两线汇合、针脚自然消失）。全年约 669.9 小时通话因此画进时间轴，而不是做成统计页；也让“分开不等于变淡”在画面上成立。
- 正常翻页、时间轴跳转都有效；时间轴跳转应直接切换到目标节点，动画较短，不要求经过所有中间页面。

### 3.2.1 真实互动星群：数据与视觉映射（v1.2 新增）

- **数据来源**：`朋友圈双向互动-日期与方向.json`，共 952 条；其中重新联系前（2016-02-14 至 2025-11-12）为 **778 条**。原始数据保持不变；生成的 `E03-点赞互动-时间聚合.json` 包含逐年、逐季度统计。**不区分方向**；同一日期出现多条互动时按多条保留。
- **时间含义**：日期是朋友圈的**发布时间**，仅作为点赞互动的时间近似，**不是准确点赞时刻**。星群不对当时的情感、谁更在意谁做推断。
- **位置**：按季度映射到 2016–2025 的远景时间轴，共 40 个季度桶，**39 个有记录，2022 年 Q4 为 0**，因此那里留白。2016 Q1 只有从初识后开始的记录；2025 Q4 只统计 11 月 12 日及以前。
- **数量到视觉星点的映射（第一轮设计阈值）**：1–4 次→1 颗；5–14 次→2 颗；15–29 次→3 颗；30–49 次→4 颗；50 次及以上→5 颗。每个季度的点聚成小星群，辅以很淡的光晕，保持固定的随机错落位置。不生成 778 个独立节点，也不在游戏中展示次数。
- **播放**：普通翻页／节点跳转约 0.6–0.9 秒完成星群依次亮灭；跨年跨度越大不必越慢。可提供原型调试用“重播星光”，但游戏里不是玩家必须操作的功能。
- **历史分布**：2016 年末、2017 年 Q2、2021 年 Q2–Q3 较密；2022 Q4 无记录；2023–2025 相对疏。**不人为制作靠近 2025 年越来越亮的故事性渐变。**

**视觉优先级**：两条曲线与记忆节点仍然是导航；星群专注表现过去的联系；2026 年进入月份放大视图后，点赞星群退场，通话针脚与共同在场的轨迹负责表现这一阶段。不把全部元素挤在同一时间尺度里。

### 3.3 2026 年的“时间放大”（已确认）

2016–2025 年采用**十年远景**。时间推进到 2026 年时，**时间带的占位尺寸不变，内部的刻度、轨迹和记忆节点平滑展开**：年份尺度让位于月份／关键时段尺度。倒退到 2025 年及以前时收拢回来。

2026 内部可以在 1 月、2 月、9–10 月等线下／线上阶段出现不同的轨迹形态：线上关系建立并不等于共同在场；2 月 24 日–3 月 8 日第一次线下相聚、9 月 19 日起回国与旅行、求婚、领证的共同生活画为同一条线，约 10 月下旬他返回德国时重新分成两条（具体返德日期待确认）。**分开不意味着关系变淡**；两条轨迹可以比此前更近。

在 2026 的时间带里，同一年可以排列多个记忆节点；对应页面既可按大体发生顺序，也可把同一时期的“天空”“小日子”“旅行”等场景编成单元。**不另外引入一套需要学习的目录操作**。

### 3.4 动效与操作边界

只把精力放在三类动效：翻页时指针滑行与星点点亮；进入／退出 2026 时的刻度放大／收拢；两条线因实际共同在场而汇合／分开。相册照片本身只做轻微翻页／淡入，**不做从时间线飞进书页的动画**。

支持左／右方向键与画面按钮翻页、鼠标点击时间节点跳转、`Esc` 退出。进入相册后隔离角色移动与游览镜头；关闭后恢复。允许按实际页面直接跳转，不设置阅读任务或解锁条件。触屏支持是可选增强，电脑浏览器为交付目标。

**私人语言槽位**：2026 年的手账页各留一个小标签位置，每页至多一句真实原话。目前仅放一个示例：天空页「我脑子里想不到第二个人」。其余句子由用户自行挑选，不由 Agent 预填。

## 5. 留白的具体含义与用法

**不是“没拍所以遗憾”，而是“有时候我们忙着幸福”。** 她喜欢出片，你想记录 Vlog；正因如此，未留下影像的亲密时刻才显得真实。相册不能反过来教训她不要拍照，也不应故作深沉地空出十几页。

采用三处不同含义的留白：

- **跨年视频**：本应留下一张截图，结果忘了；空相框旁放实际留下的几句聊天。相框做成**竖屏手机通话框**。
- **求婚**：没有刻意找人拍下现场；旁边保留戒指照片和求婚词节选，**现场本身留给记忆**。相框做成**空白拍立得**。
- **未来**：尚未发生，留一张真正等着以后被填满的空相纸。相框做成**尚未显影的相纸**，带乳白雾感。

三处相框形状不同，翻到第三个时她能自己意识到这三次空白不是同一回事，无需文字解释。

求婚的空相框与下一单元丰富的领证照片相邻，形成一次视觉节奏变化。不要每次空白都加长篇解释，更不要把留白做成游戏谜题。

## 6. 跨彩蛋关系与技术范围

- **E04 情书**：画册提取真实时间、照片和少量原话，完整的《Day One》《汉堡王》《理想主义与王冠》等留在文集。可选文字指向文集，但不必为此新增复杂的跨房间传送。
- **E01 王冠 / E02 蛋糕与仪式**：时间画册独立可用，不作为仪式的前置条件；未来页与生日演出的联动仅作候选增强。
- **C01 2048**：在旅行或飞机回程页留一个生活脚注，不再内嵌第二套 2048。
- **C02 百醇 / E05 猫抓痕**：可以在画册中一笔带过，也可以完全留给场景实物，不必强制交叉引用。
- **实现**：复用 Godot 已有的 F 交互、输入隔离、阅读页状态及退出恢复机制；为相册新建数据驱动的记忆单元、可点击时间带、缩放与星点显示。网页首版不用新增自由抓取、物理翻书或复杂视频剪辑系统。

## 7. 原型 / 成品边界

配套 HTML 原型主要验证：**双页构图、底部双轨、单人／双人／2026 拼贴／空相框差异、翻页同步、年份跳转、季度星群亮灭、2026 放大**。它不是 Godot 集成版本，不用原型图冒充真实照片，也不代表最终美术、内容或历史日期已经核实。

已批准实施顺序：先用现有示意素材打通共用数据、Godot 时间轴和电视柜入口，再补齐 13 个单元并在真实网页验证；真实照片后续替换，不作为开工前置条件。

## 8. 素材与待确认事项

**用户随后补充**：① 朋友圈互动日期和方向**已提供并完成按季度聚合**，后续只需确认展示效果；② 她非洲外派、琴行教古筝、新疆旅行的具体年份及照片，与你同年的照片；③ 初见／旅行／求婚戒指／领证／天空等实拍；④ 2026 生活碎片与可能采用的私人短句（用户自选）；⑤ 他 10 月下旬返德的日期，用于时间轴分线。

**仍待选择**：具体每个单元页数与最终文字；时间轴两条线的颜色、星群密度阈值及过渡速度；未来页是否与生日仪式产生轻联动；网页私密发布策略。

**首版验收重点**：在 1366×768 与 1920×1080 下照片和文字可看清；左右翻页、直接跳转、跨 2025/2026 的伸缩和反向返回不跳错；星群按真实朋友圈发布日期聚合、无虚构日期；阅读退出后原场景操作恢复；画册完整阅读无需触发任何其他彩蛋。

## 9. 面向实施的建议

以现在的 Godot + Blender 技术路线，不需要换引擎，也不需要真的建模一本能翻页的 3D 书。

我建议直接沿用 Stage 1 情书文集的思路：

3D 小屋负责承载画册入口，Godot 的 2D UI 负责呈现画册内容。

也就是玩家走到画册前按 `F`，进入一个覆盖在游戏画面上的精致阅读界面。它可以保留小屋背景，也可以展示完整的双页相册、照片、时间轴和动画。退出后回到正常的 3D 游览。

你想要的并不是物理模拟，而是一个视觉上融入游戏、交互上足够自然的画册界面。这会比制作真正的 3D 翻页简单得多，而且照片和文字也更清晰。

### 结合你仓库的现状，实际怎么做？

我检查了当前代码，已经有两个非常接近的实现：

- `godot/letters_ui.gd`：使用 `CanvasLayer` 构建双页阅读界面，包括纸张、文字、图片、翻页和返回。
- `godot/phone_2048.gd`：同样使用 `CanvasLayer`，并且通过 `Tween` 实现方块滑动、缩放等动画。

`playroom.gd` 也已经有完整的交互模式切换、释放鼠标、Esc 返回游览等逻辑。

所以 E03 不需要重新发明一套系统，主要是新增画册的视觉组件和时间轴逻辑。

### HTML 原型中的效果，Godot 能还原多少？

| HTML 原型效果     | Godot 实现方法                      | 判断     |
| ------------- | ------------------------------- | ------ |
| 双页手账、纸张、贴纸    | `Control`、`Panel`、`TextureRect` | 容易     |
| 多张照片自由排版      | `TextureRect` + 旋转、缩放、层级        | 容易     |
| 点击节点跳转、左右翻页   | `Button` + 页面状态                 | 容易     |
| 双轨曲线和记忆节点     | 自定义 2D 绘制或 `Line2D`             | 可实现    |
| 星星逐个亮起、熄灭     | `Tween` 驱动透明度、亮度                | 可实现    |
| 2026 年时间轴动态放大 | 插值改变时间映射和曲线位置                   | 需要专门开发 |
| 空相框、求婚与领证转场   | 2D 图片和简单过渡动画                    | 容易     |

Godot 原生提供可自定义的 UI 控件、2D 曲线绘制和属性插值动画，这些都是正式支持的能力。


这里需要说明：Godot 可以实现同样的视觉和交互效果，但不能直接把 HTML/CSS 复制到 Godot UI 中运行。 CSS 布局、SVG 时间轴和动画需要转换成 Godot 对应的实现。 我们可以先用 HTML 对齐视觉效果，然后再尽量复用已有的素材和设计。

### 那么，HTML 原型还有什么价值？

价值非常大。

之前做的 HTML 原型可以作为视觉与交互的参考标准。我们已经知道最终想要什么布局、什么动效、什么页面节奏，Agent 不用再凭文字猜测。

当然，还有第二条路线：直接把 HTML 界面叠加在 Godot 的网页游戏上。

Godot Web 支持通过 `JavaScriptBridge` 与浏览器页面交互，因此技术上可以在打开画册时显示 HTML 层，关闭时隐藏。


这种方式可以最大程度复用现有 HTML 原型。但会产生两套 UI 和输入体系，需要处理键盘焦点、鼠标捕获、Esc、窗口尺寸和构建发布等集成问题。

目前我依然推荐 Godot 原生 UI，因为你已经有运行中的阅读系统，而且 E03 的交互规模不大。

不过，如果后续发现 HTML 版本的视觉效果远好于 Godot 版本，而迁移成本又明显过高，HTML Overlay 可以作为备选。你的交付目标本来就是浏览器，因此没必要为了技术纯粹性拒绝它。

### 下一步应该怎么推进？

我建议先让 Codex 做一个很小的 Godot E03 技术与视觉 Spike，不急着导入全部真实照片。

只实现三个代表性状态：2020 年双人对照页、真实季度星群经过指针时的依次亮灭、2026 年时间轴平滑放大。要求在真实的 Godot Web 导出中运行，并与目前 HTML 原型比较效果。

这三个状态如果能够达到预期，其余画册内容基本就是图片排版和数据填充。

我的判断是：这件事的主要难点已经不是技术能否做到，而是如何让 Godot 版本保留 HTML 原型的美术品质。 不需要为这个画册引入更重的 3D 方案，也不需要牺牲我们已经设计好的时间轴动效。
